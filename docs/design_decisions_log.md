# Design Decisions Log

Thesis: MongoDB-based shipment tracking pipeline (event ingestion, batch ETL, benchmarking)

How to use: add a new row whenever a decision is made. Never delete old decisions; mark them "Superseded" and add the new one.

## Decided

| ID | Decision | Alternatives considered | Reason | Trade-off / downside | Status |
|---|---|---|---|---|---|
| D-01 | Store events in a separate `events` collection, not embedded in `shipments` | Embed events array in the shipment document | Unbounded array growth; better for high-frequency append-only inserts | Latest-status and history need separate reads | Decided |
| D-02 | Two ingestion paths: direct insert and bulk insert | Bulk only; API insert only | Direct insert shows a realistic per-event flow with status updates; bulk gives raw database throughput and fast large-dataset generation | Two code paths to maintain and compare | Decided |
| D-03 | Batch ETL for analytics (not real-time aggregation) | Real-time aggregation on every insert | Fits scope and the thesis plan; simpler to validate | Metrics are not real-time | Decided |
| D-04 | FastAPI as the API layer | Flask, Django REST | Async support, Pydantic validation, automatic Swagger docs | None significant | Superseded by D-24 |
| D-05 | Docker Compose for deployment | Manual local install | Reproducible, clean-database restarts for benchmarks | Docker overhead on a laptop | Decided |
| D-06 | No full UI; Swagger UI plus optional Streamlit dashboard | Full web application | Thesis focus is data engineering and performance, not interface design | Less visual polish | Decided |
| D-07 | Out of scope: authentication, sharding, multi-node clusters | Include them | Keeps the project within thesis size | Listed as future work | Decided |
| D-08 | Add couriers collection and optional courier_id on events | No couriers; courier info embedded in events | Enables per-courier ETL metrics (success rate, failed attempts) | One more reference collection and one more index on events | Decided |
| D-09 | Keep a denormalized current_status in shipments, updated per insert batch on the direct path | Derive status from the latest event at query time | Latest-status query is a single read by _id (NFR-03) | Extra write per batch; needs the out-of-order rule in section 5 | Decided |
| D-10 | Update current_status only when the new ts is newer than last_event_ts | Always overwrite | Late events must not overwrite newer status | Conditional update per shipment | Decided |
| D-11 | ETL window is one day, `[start, end)` on `events.ts` | Hourly window; one run over the whole dataset | Matches the daily schedule, and a day is a natural unit for reports and reruns | Metrics are available only after the day ends | Decided |
| D-12 | Average delivery time = `delivered` event `ts` minus `shipments.created_at` | From the first `picked_up` event | Simplest; needs only a `$lookup` on the indexed `_id` | Includes time before pickup, so it is less precise than pickup-to-delivery | Decided |
| D-13 | Success rate is attempt-based: delivered / (delivered + delivery_failed) | Shipment-based (share of shipments delivered on the first try) | Matches the existing courier query and FR-09 | Counts repeated attempts of the same shipment separately | Decided |
| D-14 | `events_per_hub` counts only facilities with `type: "hub"`; hub IDs are read once in Python | Count all `facility_id` values; `$lookup` into `facilities` | Matches "per hub" in FR-09; `facilities` is tiny, so no join is needed | One extra small read per ETL run | Decided |
| D-15 | Rerun: upsert, then delete same-period documents with another `run_id`; the daily job also recomputes the previous day | Insert only; delete the whole period before writing | Reruns never duplicate, stale metrics are removed, and late events are caught | Two days are recomputed every night | Decided |
| D-16 | `ts` and `created_at` are stored as BSON `Date`, not ISO strings | ISO strings | `$dateTrunc` and `$subtract` need real dates; dates also sort and compare correctly | The generator must produce real datetime values | Decided |
| D-17 | bulk-loaded shipments get current_status computed by the generator; bulk loader only inserts shipments and events, does not run AP-04 | post-load $merge pass; no status on bulk data | NFR-03 and FR-06 must work on 1M/10M datasets, and bulk throughput stays clean | the direct path does extra status writes that bulk doesn’t, so report this when comparing the two | Decided |
| D-18 | Direct insert path: the generator pre-creates shipments with no current_status field, then inserts events. |  | AP-04 needs existing shipment documents | shipments must exist before their events arrive | Decided |
| D-19 | Idempotent inserts: each event's `_id` is its unique `event_id`; events are written with `insert_many(ordered=False)` and duplicate key errors (code 11000) are ignored, any other write error is raised | Upsert per event; check for existence before insert | Meets NFR-07; a retried batch cannot create duplicates, and an unordered insert keeps writing past a duplicate; keeps insert_many speed for the benchmarks | The generator must create unique, repeatable event IDs; duplicate errors must be told apart from real errors | Decided (resolves O-04) |
| D-20 | ETL scheduler: APScheduler cron trigger at 01:00 UTC, in its own container; the CLI is kept for manual and benchmark runs | Sleep loop; system cron running the CLI | Cron-style trigger in a few lines of Python, no OS cron setup in the container | One extra dependency | Decided |
| D-21 | The generator gives the events of one shipment strictly increasing `ts` values | Allow equal `ts` and let the first generated event win | No ties, so the direct path (AP-04) and the bulk path (D-17) always give the same current_status (acceptance criterion 2) | Slightly less realistic: real scanners can produce equal timestamps | Decided |
| D-22 | `events` is a regular collection with secondary indexes | Time-series collection; bucket pattern | A time-series collection has no unique `_id` index, so D-19 (idempotent inserts) would not work; regular collections support all planned indexes (O-02) | No automatic bucketing or compression, so storage is larger at 10M events | Decided (resolves O-01) |
| D-23 | FastAPI uses the synchronous PyMongo client; endpoints are plain `def` functions | PyMongo async API (`AsyncMongoClient`); Motor | Same driver and query code as ingestion, ETL and benchmarks; FastAPI runs `def` endpoints in a thread pool, so blocking database calls do not block the server | FastAPI's async support is not used; concurrency is limited by the thread pool size | Decided |
| D-24 | FastAPI as the API layer | Flask, Django REST | Pydantic validation of requests and responses, automatic Swagger docs (the only UI, D-06) | None significant | Decided (supersedes D-04) |
| D-25 | Events by facility (AP-07) and by courier (AP-11) return at most `limit` events sorted by `ts`, default 100; shipment history (AP-06) has no limit | No limit; cursor pagination | At 10M events one facility can have hundreds of thousands of events in a window; a limit keeps responses small and latency stable. History stays complete because FR-07 requires the full history and one shipment has only a few events | Clients must narrow the time window to see more; no pagination yet | Decided |
| D-26 | Read-only API: `GET /shipments/{id}/status` (AP-05), `/shipments/{id}/events` (AP-06), `/facilities/{id}/events` (AP-07), `/couriers/{id}/events` (AP-11), `/metrics` (AP-10), `/health`; `limit` is 1 to 1,000; unknown shipment: status returns 404, history returns an empty list | Write endpoints (POST shipments/events); 404 for history of an unknown shipment | Data enters only through the generator and loaders (D-02); history stays one query, so its measured latency is not inflated (NFR-02); status reads the shipment document anyway, so 404 is free there | No API for adding data; history cannot tell "unknown shipment" from "no events yet" | Decided |
| D-27 | Event lifecycle: `label_created` → `picked_up` → `arrived_at_hub` → `sorted` → (`in_transit` → `arrived_at_hub` → `sorted`, only between different cities) → `out_for_delivery` → `delivered`. Each delivery attempt fails (`delivery_failed`) with probability 0.10; after 3 failed attempts the shipment is `returned`. Couriers handle `picked_up`, `out_for_delivery`, `delivered`, `delivery_failed` | Random event types; replaying real carrier traces | Realistic order based on carrier tracking APIs (requirements section 4); produces failure and per-courier data for the ETL (FR-09); simple to test | No lost parcels, customs or multi-hub routes | Decided |
| D-28 | Dataset: shipments are created at random times over a 30-day period from 2026-03-01; events after the period end are dropped, so the last shipments are still in progress; shipments are generated until exactly N events (FR-12); the generator yields one shipment at a time; timestamps are whole seconds | Fixed number of shipments; build the whole dataset in memory | Dataset sizes are defined in events, and an exact count makes the NFR-06 check simple; memory stays flat at 10M events; BSON dates keep only milliseconds, so whole seconds survive the round trip unchanged | Events per day grow with dataset size; the last shipment can be cut short | Decided |
| D-29 | IDs: shipments `SHP-0000001` (7 digits); events `<shipment_id>-<seq>`, e.g. `SHP-0000001-03` | ObjectId; global counter (`evt_000123`) | Unique and repeatable for the same seed (D-19) without global state; an event ID shows its shipment | Longer strings; at most 9,999,999 shipments (10M events need about 1.1M) | Decided |
| D-30 | The direct inserter writes shipments in generation order (all events of one shipment, then the next), in batches of `batch_size` (O-03); it is a CLI run from the host or with `docker compose run`; `--reset` rebuilds shipments, events, reference data and indexes | Replay events in global time order across shipments; a long-running service | Simple code; batches still mix several shipments; every run can start from a clean state (D-05) | Late events across shipments are rare, so the out-of-order rule (D-10) is covered by tests rather than by the inserter | Decided |
| D-31 | Bulk loader writes events in chunks of 10,000 by default (configurable) | 1,000; 100,000 | Much larger than the direct batches, so the two paths differ clearly; memory stays small; PyMongo can send it as one `insert_many` | The value is a sensible default, not an experiment result | Decided |
| D-32 | Insert experiment: methods single (100k only), batches of 100 / 1,000 / 5,000, and bulk; index configs none / minimal / full; 100k and 1M events (10M in Month 6); 3 runs each with the same seed, reporting the median; each run starts from a reset `tracking_benchmark` database; only database calls are timed, with insert and status time recorded separately (D-17); it runs inside Docker | Run from the host; include generation time; test every combination at 10M | Results show the database rather than Python or Docker Desktop networking; a separate database keeps the demo data safe; about one hour in total | Single inserts are not compared at 1M; time spent encoding documents in PyMongo is still included | Decided |
| D-33 | Direct insert batch size is 1,000 events (still configurable) | 1; 100; 5,000 | Experiment D-32 at 1M events, `minimal` indexes: 1,000 is about twice as fast as 100 (40,359 vs 21,490 events/s), while 5,000 adds only about 9% (43,898) for batches five times larger; single inserts miss NFR-01 at 100k (about 700 events/s) | Not the fastest measured option; based on one laptop | Decided (resolves O-03) |
| D-34 | Query experiment: AP-05, AP-06, AP-07, AP-11 on 100k and 1M events (10M in Month 6; AP-10 after the ETL) with index configs none / minimal / full; data loaded with the bulk loader into `tracking_benchmark`; 3 rounds on the same data, 1,000 calls per round (100 for full scans) after unmeasured warm-up calls; one client, one request at a time; report p50 / p95 / p99 and `explain()` plans; database level for all queries, API level for AP-05 and AP-06 | Average latency only; same call count for scans; concurrent load test | p95 is what NFR-02 and NFR-03 require; scans are about 300 times slower than indexed reads, so equal counts would take hours; `explain()` shows why a query is fast or slow | Fewer scan calls give a less precise p95; results do not show behaviour under many users or during writes | Decided |
| D-35 | The partial index `events_courier_ts` uses the filter `courier_id > ""` instead of `$type: "string"` | Keep `$type` and add it to the AP-11 query; ordinary index without a filter | With `$type`, MongoDB did not use this index for a plain AP-11 query and read 34,772 documents to return 53 at 1M events (D-34). With `$gt` it reads 53, the query stays unchanged, and null values stay out of the index | The filter is less obvious to read, so it needs a comment; relies on all courier IDs being non-empty strings | Decided |
| D-36 | Use the `full` index set for `events` and `analytics`; re-check `events_ts` when the ETL is measured | `none`; `minimal` | At 1M events `full` serves AP-07 and AP-11 in 1.3 to 1.5 ms (p95) instead of 460 to 610 ms with `minimal`, keeps latency flat from 100k to 1M (NFR-04), and still meets NFR-01 (29,003 events/s at batch 1,000) | About 28% less insert speed than `minimal` at batch 1,000; `events_ts` serves only the ETL (AP-08), so its value is not proven yet | Decided (resolves O-02); `events_ts` re-checked in D-37: the ETL runs 2 to 3 times faster with `full` than with `minimal` (9.6 vs 23.4 s per day at 10M events), so `full` stays |
| D-37 | Month 6 experiments at 10M events: insert test with `full` indexes, batch 1,000 and bulk only; query test with `full` only, plus AP-10 after an ETL run at 100k, 1M and 10M; new ETL runtime test at 100k, 1M and 10M with `minimal` vs `full` (re-checks `events_ts`, D-36), timing 7 days (2026-03-08 to 2026-03-15) and reporting seconds per day; 3 repeats each; the demo database stays at 100k | Every combination at 10M; time all 30 ETL days | `none` and `minimal` are already compared at 1M; at 10M, scans take about 5 s each and the full matrix would take many hours; the ETL works one day at a time (D-11), so seconds per day is the natural unit; about 2 hours in total | 10M has fewer combinations than 1M; at 10M the indexes (about 1 GB) fit in MongoDB's 3.4 GB cache, but data and indexes together nearly fill it (87% used, about 1.16M pages read back from disk during the load; `benchmarks/results/index_sizes_10m.txt`), which is the probable cause of the slower inserts at 10M; data much larger than memory is not tested | Decided |
| D-38 | No geospatial (`2dsphere`) index and no location queries | Add a `2dsphere` index on event location with a "near a point" query | No requirement or access pattern (FR-01 to FR-15, AP-01 to AP-11) needs location search; the experiments compare the indexes the queries really use | Location is stored on events but cannot be searched efficiently; would need a new index and access pattern later | Decided (resolves O-05) |
| D-39 | No dashboard; Swagger UI and the benchmark charts are the only interface | Streamlit dashboard for metrics and benchmark results (FR-14, "Could") | FR-14 is optional; Swagger UI already shows all API results and `benchmarks/results/` holds the charts; D-07 keeps the UI minimal and the time goes to the experiments | No visual overview for non-technical users; FR-14 is not implemented | Decided (resolves O-06) |
